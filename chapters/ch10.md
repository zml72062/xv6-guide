# 10. 内核态中断处理

本章和接下来的一章研究 xv6 中最有趣的主题之一: **内核态和用户态的切换**. 回忆一下, xv6 内核工作在 **S 模式**, 而用户进程工作在 **U 模式**. 我们知道, 在 RISC-V 中, 导致处理器特权模式从 U (低级别) 切换到 S (高级别) 的唯一机制是 **中断**. 因此, 不难得出以下论断:
* 从用户态进入内核态, 意味着发生了 **中断**
* 从内核态回到用户态, 意味着 **中断返回**

> [第 3 章](ch3.md)中讨论的时钟中断是一个特例. 甚至不能在 S 模式中处理时钟中断, 而必须进入 M 模式.

即使在内核态, 中断也有可能发生. 在本章中, 我们首先讨论 **内核态中发生中断** 该怎么处理. 这是因为处理用户态中产生的中断涉及 **从用户态到内核态的陷入**, 从而更加复杂. 后一种情况将是[下一章](ch11.md)的主题.

## RISC-V 硬件对中断的支持

和之前讨论过的虚拟内存机制一样, 中断处理离不开硬件的支持. 在[第 2 章](ch2.md)和[第 3 章](ch3.md)中, 我们已经初步介绍过 RISC-V 处理器响应中断的过程. 在这里, 我们给出一个更加正式、完整的描述. 我们假设处理器一开始处于 S 或 U 模式.

1. 处理器每执行完一条指令, 便检查是否需要响应中断. 处理器会对每一类中断作如下检查:
    * 如果该中断是 **内中断** (即指令本身产生的中断) 且中断码为 i, 那么检查 `medeleg` 的第 i 位. 根据这一位为 0 或为 1, 处理器决定陷入 **M 模式** 或 **S 模式** 以处理中断.
    * 如果该中断是 **外中断** (外部设备产生的中断) 且中断码为 i, 那么
        + 首先检查 `mideleg` 的第 i 位. 根据这一位为 0 或为 1, 处理器判断该中断的级别为 **M 级别** 或 **S 级别**. 
            > 此时处理器还不一定决定 **响应中断**, 因为还需检查中断开关.
        + 根据中断的级别为 M/S, 确认 `mstatus`/`sstatus` 中的 MIE/SIE 位为 1, 且 `mie`/`sie` 的第 i 位为 1. 如果两个位都为 1, 说明 **中断开关** 处于开启, 执行下一步; 否则, 不响应中断.
        + 检查 `mip`/`sip` 的第 i 位. 如果为 1, 说明有中断待处理; 根据中断的级别为 M/S, 处理器决定陷入 **M 模式** 或 **S 模式** 以处理中断. 否则, 不响应中断.

        如果确实有待处理的外中断, 则处理器可以通过 `mip`/`sip` 中为 1 的位确定其类型.

> 我们看到, RISC-V 处理器对待内中断和外中断有许多不同之处:
> * 可以通过中断开关 "关闭" 外中断, 但不能 "关闭" 内中断. 这是因为, 内中断往往来源于处理器 "取值-执行" 循环中的故障; 如果不响应内中断, 处理器根本无法按正常的指令流执行下去.
> * 外中断到来时, `mip`/`sip` 寄存器会 "提醒" CPU 有待处理的外中断. 对于内中断则无这样的寄存器.
>
> 不过, 内、外中断的区别只存在于 "处理器决定是否响应中断" 这一步. 等到实际处理中断的时候, 两者就不再区别对待.

假定在第 1 步中, 处理器 **决定陷入 X 模式** (X 为 M/S) 处理中断. 那么处理器接下来就完成一些例行公事: 

2. 将当前处理器特权级别存入 `xstatus` 寄存器的 XPP 字段, 然后将特权级别切换为 X.
3. 将 `xstatus` 中的 XIE 位保存到 XPIE 位, 然后令 XIE 位为 0. 这样, 我们在 X 模式下 **关闭所有外中断**.
4. 填写 `xcause` 寄存器. 该寄存器用于向软件 (操作系统) 报告中断原因.
    * 对于外中断/内中断, `xcause` 的最高位分别填 1/0.
    * `xcause` 的剩余位填入中断码.
5. 对于内中断, 如果产生了错误码, 则将错误码填入 `xtval` 寄存器.
6. 把当前 `pc` 存入 `xepc` 寄存器.
7. 把 `xtvec` 寄存器的值复制到 `pc`.
> 这里我们假设 `mtvec`/`stvec` 中存有 4 字节对齐的地址. RISC-V 还允许在第 7 步中根据不同的中断码将 `pc` 设置为不同的地址, 但是 xv6 不使用这一特性.

在这里, 6、7 两步合称为 **交换中断向量**, 其效果是使程序的正常执行被打断, CPU 跳转到地址 `mtvec`/`stvec` 处的指令接着执行.

通过上面的描述, 我们看到: 中断处理最初的工作是由 **硬件** 完成的. 这些工作是 **共性的**; 也就是说, 不论发生什么种类的中断, 硬件都执行一模一样的步骤. 针对不同种类的中断作出 **个性化的** 处理, 是 **软件 (操作系统)** 的工作. 具体来讲, 操作系统应该:
* 事先编写好中断处理程序. 在系统启动时, 将处理程序的 **入口地址** 写入 `mtvec`/`stvec` 寄存器.
* 在中断处理程序中, 根据 `mcause`/`scause`, `mtval`/`stval` 判断中断的类型和原因, 并跳转到合适的分支执行具体的中断处理工作.
* 处理完成后, 使用 **`mret`/`sret` 指令** 回到正常指令流.

本章的剩余部分及[下一章](ch11.md)将介绍 xv6 如何配合硬件完成中断处理的工作.

> RISC-V 中, `xret` 指令 (`x` 为 `m`/`s`) 会导致处理器做如下工作:
> * 将 `xstatus` 中的 XIE 位设为 XPIE 位存储的值, 然后令 XPIE 为 1.
> * 特权级别被设为 `xstatus` 中 XPP 字段的值, 然后把 XPP 字段清零.
> * 把 `xepc` 中的值复制到 `pc`.
> 
> 这样, 处理器会回到 **中断发生时刚执行完的那条指令** 重新开始执行.

## Recap: 时钟中断处理

在 xv6 中, 对时钟中断的处理不同于其他种类的中断. 这是因为时钟中断是唯一需要 **陷入到 M 模式** 才能处理的中断. 在[第 3 章](ch3.md)中, 我们已详细介绍过 xv6 对时钟中断的处理流程. 我们在此简要总结如下:
* 在 xv6 启动时, 通过 `timerinit()` 函数完成时钟中断处理的初始化:
    + 为每个 CPU 核心分配 40 字节物理内存, 其中存放有 **该核心的 `mtimecmp` 寄存器的内存映射地址**, 以及 **每两次时钟中断相隔的周期数** 等重要信息. 将这 40 字节内存的基址存入 `mscratch` 寄存器.
    + 将函数 `timervec()` (定义在 `kernel/kernelvec.S[93:124]`) 的首地址存入 `mtvec` 寄存器.
* 时钟中断发生时, 硬件跳转到 `timervec()` 函数. 它完成以下工作:
    + 修改 `mtimecmp` 寄存器的值, 以设定下一次时钟中断发生的时间.
    + 修改 `sip` 寄存器的值为 `0x2`, 从而向 S 模式 **转发** 一个 supervisor software interrupt (SSI, 中断码为 1 的外中断).
    + 使用 `mret` 指令返回 U 或 S 模式.

    值得注意的是, `timervec()` 本身只完成尽可能少的工作, 而把更复杂的处理 **转交给 S 模式下的 SSI 中断处理函数** 完成.

一般来讲, 为了处理任何一种中断, 通常需要编写两个函数:
* **中断处理初始化函数**. 类似于 `timerinit()`, 这个函数在系统启动时执行, 为中断处理做准备 (设置有关寄存器, 在内存中维护必要的数据结构, 等等).
* **中断处理函数**. 类似于 `timervec()`, 它是实际处理中断的函数.

在本章的剩余部分中, 我们将看看 xv6 如何对 **时钟中断以外的中断** 完成以上两部分的工作.

## xv6 内核态中断处理初始化

在 `main()` 函数中, 通过调用 `trapinit()` 和 `trapinithart()` 来完成中断处理的初始化工作: (`kernel/main.c[23:24]`)
```c
    trapinit();      // trap vectors
    trapinithart();  // install kernel trap vector
```
这两个函数的定义分别在 `kernel/trap.c[19:23]` 和 `kernel/trap.c[25:30]`:
```c
void trapinit(void)
{
  initlock(&tickslock, "time");
}

void trapinithart(void)
{
  w_stvec((uint64)kernelvec);
}
```
`trapinit()` 和 `trapinithart()` 完成的工作很简单: 前者初始化了一个互斥锁 `tickslock`; 后者把 `kernelvec()` 函数的首地址存入 `stvec` 寄存器. 

> 原则上来说, 中断处理初始化函数不仅需要为 **CPU** 配置好与中断处理有关的寄存器 (必要时还包括内存), 还应该为每一种可能产生中断的 **外部设备** 做出相应的初始化工作. 前者可称为中断处理初始化的 **共性** 工作, 而后者则为 **个性** 工作. 容易看出, 上面介绍的 `trapinit()` 和 `trapinithart()` 函数只是完成了共性的工作. 为什么不让它们也完成个性的工作呢 (就像用于初始化时钟中断处理的 `timerinit()` 那样)? 
>
> 原因就在于时钟中断有其特殊性: 它是 **唯一** 需要在 M 模式中处理的中断. 因此, 对于时钟中断的个性化处理完全可以合并到 M 模式下共性化的中断处理初始化函数中去. 对于 S 模式下的中断处理 (即我们现在所关心的情况), 由于中断的来源更为多样, 有必要采用 **分层** 的思想来简化逻辑. 具体来说, 就是让一部分函数 (包括这里的 `trapinit()` 和 `trapinithart()`) 只关心 CPU 侧的中断处理逻辑, 另一部分函数只关心 I/O 设备侧的中断处理逻辑.

## xv6 内核态中断处理函数

### `kernelvec()` 函数

在 xv6 的中断处理初始化代码中 (具体来说, 是 `trapinithart()` 函数中), 我们将 `kernelvec()` 的首地址放入了 `stvec` 寄存器. 因此, `kernelvec()` 函数就是 **内核态下的中断处理函数**. 我们现在就来研究它的实现. 

`kernelvec()` 函数是用汇编语言写的, 定义在 `kernel/kernelvec.S[10:88]`:
```asm
.globl kernelvec
.align 4
kernelvec:
    # make room to save registers.
    addi sp, sp, -256

    # save the registers.
    sd ra, 0(sp)
    sd sp, 8(sp)
    sd gp, 16(sp)
    sd tp, 24(sp)
    sd t0, 32(sp)
    sd t1, 40(sp)
    sd t2, 48(sp)
    sd s0, 56(sp)
    sd s1, 64(sp)
    sd a0, 72(sp)
    sd a1, 80(sp)
    sd a2, 88(sp)
    sd a3, 96(sp)
    sd a4, 104(sp)
    sd a5, 112(sp)
    sd a6, 120(sp)
    sd a7, 128(sp)
    sd s2, 136(sp)
    sd s3, 144(sp)
    sd s4, 152(sp)
    sd s5, 160(sp)
    sd s6, 168(sp)
    sd s7, 176(sp)
    sd s8, 184(sp)
    sd s9, 192(sp)
    sd s10, 200(sp)
    sd s11, 208(sp)
    sd t3, 216(sp)
    sd t4, 224(sp)
    sd t5, 232(sp)
    sd t6, 240(sp)

    # call the C trap handler in trap.c
    call kerneltrap

    # restore registers.
    ld ra, 0(sp)
    ld sp, 8(sp)
    ld gp, 16(sp)
    # not tp (contains hartid), in case we moved CPUs
    ld t0, 32(sp)
    ld t1, 40(sp)
    ld t2, 48(sp)
    ld s0, 56(sp)
    ld s1, 64(sp)
    ld a0, 72(sp)
    ld a1, 80(sp)
    ld a2, 88(sp)
    ld a3, 96(sp)
    ld a4, 104(sp)
    ld a5, 112(sp)
    ld a6, 120(sp)
    ld a7, 128(sp)
    ld s2, 136(sp)
    ld s3, 144(sp)
    ld s4, 152(sp)
    ld s5, 160(sp)
    ld s6, 168(sp)
    ld s7, 176(sp)
    ld s8, 184(sp)
    ld s9, 192(sp)
    ld s10, 200(sp)
    ld s11, 208(sp)
    ld t3, 216(sp)
    ld t4, 224(sp)
    ld t5, 232(sp)
    ld t6, 240(sp)

    addi sp, sp, 256

    # return to whatever we were doing in the kernel.
    sret
```
这个函数实际上并不涉及中断处理的具体逻辑, 它只是简单地 **保存现场**. 具体来说, 这个函数
* 将 RISC-V 的所有通用寄存器 (除恒为零的 `zero` 外, 一共 31 个) 全部保存到栈上
* 调用 C 语言编写的 `kerneltrap()` 函数
* 当 `kerneltrap()` 返回时, 将 **除 `tp` 外的** 所有通用寄存器值从栈上恢复
* 用 `sret` 指令返回到正常控制流

> 在第三步中, 为什么不从栈上恢复 `tp` 的值呢? 事实上, 很快就会看到, `kerneltrap()` 的执行过程中可能会发生 **CPU 的切换**. 因而 `kernelvec()` 中 *保存寄存器* (`sd`) 和 *恢复寄存器* (`ld`) 的操作可能是在 **不同的** CPU 上完成的. 上述做法可以避免把旧 CPU 的 `tp` (存储了旧 CPU 的核心号) 复制到新 CPU 的 `tp` 中, 从而保证了 **内核态下 `tp == mhartid` 恒成立**.

### `kerneltrap()` 函数

真正针对各种类型的中断作出响应的, 是 `kerneltrap()` 函数. 这个函数定义在 `kernel/trap.c[132:161]` 中:
```c
void kerneltrap()
{
  int which_dev = 0;
  uint64 sepc = r_sepc();
  uint64 sstatus = r_sstatus();
  uint64 scause = r_scause();
  
  if((sstatus & SSTATUS_SPP) == 0)
    panic("kerneltrap: not from supervisor mode");
  if(intr_get() != 0)
    panic("kerneltrap: interrupts enabled");

  if((which_dev = devintr()) == 0){
    printf("scause %p\n", scause);
    printf("sepc=%p stval=%p\n", r_sepc(), r_stval());
    panic("kerneltrap");
  }

  // give up the CPU if this is a timer interrupt.
  if(which_dev == 2 && myproc() != 0 && myproc()->state == RUNNING)
    yield();

  // the yield() may have caused some traps to occur,
  // so restore trap registers for use by kernelvec.S's sepc instruction.
  w_sepc(sepc);
  w_sstatus(sstatus);
}
```
`kerneltrap()` 执行以下流程:
* 继续保存现场. 将 `sepc` 和 `sstatus` 这两个寄存器保存在局部变量中. 当 `kerneltrap()` 即将返回时, 会从局部变量中恢复 `sepc` 和 `sstatus`. 

  这一步看似多余, 实则必要. 其原因同样在于 `kerneltrap()` 可能在执行过程中切换 CPU. 我们必须保证在新 CPU 上执行 `sret` 指令从中断返回后, 机器的状态 (包括它看到的代码和数据) 都如同在旧 CPU 上发生了一次中断返回一样. 由于 `sret` 指令会根据 `sepc` 和 `sstatus` 寄存器的内容修改 `pc` 和 `sstatus`, 我们只需确认新、旧 CPU 中 `sepc` 和 `sstatus` 寄存器的内容一致即可. 为此, 我们在这里把 (旧 CPU 的) `sepc` 和 `sstatus` 保存到栈上, 这样新 CPU 可以从栈中读取旧 CPU 中的 `sepc` 和 `sstatus`, 并将它们恢复到自己的 `sepc` 和 `sstatus` 中. (注: 新、旧 CPU 上栈的一致性由上下文切换机制自动保证, 详见[第 12 章](ch12.md)或者下面关于上下文切换的简要介绍.)
* 检查机器状态. 首先, 确认 `sstatus` 寄存器中的 SPP 字段等于 1,
    ```c
    if((sstatus & SSTATUS_SPP) == 0)
      panic("kerneltrap: not from supervisor mode");
    ```
    也就是说, `kerneltrap()` 应当 **只处理 S 模式下发生的中断**. 

    其次, 确认中断已关闭. 
    ```c
    if(intr_get() != 0)
      panic("kerneltrap: interrupts enabled");
    ```
    这是因为硬件响应中断时会自动关闭全局中断开关 (将 `sstatus` 中的 SIE 位清零).
* 调用 `devintr()` 函数判断中断的来源, 并完成相应的处理工作. `devintr()` 函数定义在 `kernel/trap.c[172:220]` 中, 其框架大致为
    ```c
    int devintr()
    {
      uint64 scause = r_scause();
    
      if((scause & 0x8000000000000000L) &&
         (scause & 0xff) == 9){
        // this is a supervisor external interrupt, via PLIC.

        // ... ... code for interrupt processing ... ...
    
        return 1;
      } else if(scause == 0x8000000000000001L){
        // software interrupt from a machine-mode timer interrupt,
        // forwarded by timervec in kernelvec.S.

        // ... ... code for interrupt processing ... ...
    
        return 2;
      } else {
        return 0;
      }
    }
    ```
    `devintr()` 函数有 3 个分支:
    * **Supervisor external interrupt** (SEI), 对应于 `scause == 0x8000000000000009L`. 这类中断是由 **外部设备** (磁盘, 或 UART 输入输出设备) 产生的. 对于这类中断, `devintr()` 会调用 PLIC 硬件提供的接口, 来判断到底是 **什么设备** 引发了中断, 然后调用相应设备的中断处理程序来响应中断. 完成处理后, `devintr()` 返回 1.
    * **Supervisor software interrupt** (SSI), 对应于 `scause == 0x8000000000000001L`. 这个中断是由 M 模式下的时钟中断处理程序转发给 S 模式的. 此时, `devintr()` 会做相应的处理, 并且返回 2.
    * **其他中断**. 假如接收到的中断属于内中断 (例如缺页、系统调用), 或者是类型未知的外中断 (既非 SEI 也非 SSI), 那么 `devintr()` 不做处理, 直接返回 0.

  在 `kerneltrap()` 函数中, 会根据 `devintr()` 的返回值做出不同的动作:
  + 如果 `devintr()` 返回 0, 说明内核收到一个内中断, 或者一个类型未知的外中断. 此时内核会 panic:
    ```c
      if((which_dev = devintr()) == 0){
        printf("scause %p\n", scause);
        printf("sepc=%p stval=%p\n", r_sepc(), r_stval());
        panic("kerneltrap");
      }
    ```
    > xv6 对于内核模式下发生的内中断采用非常简单粗暴的处理方式: 它认为这类内中断的产生代表着内核发生了不可恢复的致命错误, 从而必须停止其运行.
  + 如果 `devintr()` 返回 2, 说明内核收到一个 supervisor software interrupt. 这表明刚刚发生了一次时钟中断. 此时, 内核会检查当前 CPU 上是否有进程在运行; 如果有的话, 会调用 `yield()` 令该进程把当前 CPU 的执行权转让给下一个进程:
    ```c
      if(which_dev == 2 && myproc() != 0 && myproc()->state == RUNNING)
        yield();
    ```
    我们会在[第 12 章](ch12.md)中介绍 `yield()` 函数的细节. 简要来说, 假如当前 CPU 上正在运行的进程是 `p`, 那么 `yield()` 会把上下文 (包括 `ra`, `sp` 及所有 callee-saved 寄存器) 保存到 `p.context` 字段中, 然后让调度器重新选择一个进程 `q` (`q` 可能与 `p` 相同, 也有可能不同), 从 `q.context` 中恢复出上下文并接着执行. 这里就会分出两种情况:
      * 情况 1: `q == p`. 也就是说, 接下来还是由进程 `p` 在当前 CPU 上执行. 这时候, `yield()` 函数就没有任何效果. 于是当前 CPU 会接着完成 `kerneltrap()` 的剩余代码, 然后返回到 `kernelvec()` 中. 
      * 情况 2: `q != p`. 在这种情况下, 当前 CPU 会把执行到一半的中断处理程序暂时搁置, 转而执行进程 `q` 上一次停下来时的代码. 
      
        那么, 要等到什么时候才会把中断处理程序的后半部分执行完呢? 一种可能的回答是: 等到当前 CPU 再经历若干轮时钟中断后 (在此期间 `yield()` 又被调用了多次), 进程 `p` 再度被选中运行的时候, 就会接着完成剩余的中断处理代码. 
        
        不过, 别忘了我们有 **多个** 处理器核心! 因此, 还存在这样的可能性: 在稍后的时刻, 另一个 CPU 也收到了一个时钟中断, 从而引发一次 (新的 CPU 上的) `yield()` 调用; 在新的 CPU 上, 调度器恰好选中了刚刚被暂停下来的进程 `p`, 使其恢复运行. 这时候, `p.context` 中的上下文会被恢复到新的 CPU 上, 从而中断处理代码会 **转移到另一个 CPU 上** 继续执行.
* 在 `kerneltrap()` 的最后, 恢复 `sepc` 与 `sstatus` 寄存器为此前保存的值.
  ```c
    w_sepc(sepc);
    w_sstatus(sstatus);
  ```
> 我们看到, 由于有多个核心并行地执行指令, 中断处理程序有可能 **在中途切换 CPU**. 我们必须保证 **切换 CPU 不会导致中断处理程序发生错误**. 为此, 需要保证切换 CPU 前后 **寄存器、内存状态** 的一致性. 
>
> 首先, 我们检查寄存器状态的一致性. 寄存器分为三类: **callee-saved 的通用寄存器**, **caller-saved 的通用寄存器**, 以及各种 **CSR**. 
>
> 对于前两类寄存器, 我们实际上无需担心其一致性: 上下文切换机制已确保 `ra`, `sp` 及所有的 callee-saved 通用寄存器被正确地从旧 CPU 复制到新 CPU; 一旦栈指针 `sp` 被正确恢复, 则所有的 caller-saved 通用寄存器 (`tp` 除外, 因为它存储 CPU 核心号, 本来就不应该在切换 CPU 前后保持一致) 可以从栈中正确地恢复. 对于 CSR, 我们主要关心的是 `sepc` 和 `sstatus` 的一致性, 因为只有这两个 CSR 与中断返回后的机器状态相关. 而这两个寄存器已经分别在 `kerneltrap()` 的开头和结尾被正确地保存和恢复.
> 
> 其次, 我们检查内存状态的一致性. 在[第 7 章](ch7.md)末尾我们曾经指出, 内核态下所有的 CPU 共用一张页表. 因此, 切换 CPU 前后, 虚拟地址到物理地址的对应关系保持不变, 从而自动保证了旧 CPU 和新 CPU 看到的地址空间是完全相同的. 但是要小心: 如前所述, 新、旧 CPU 的 `tp` 寄存器是不同的, 所以当我们用某个依赖于 `tp` 的指针进行访存的时候 (例如, 在某个数组中取下标等于 `tp` 的元素), 所得到的内存的内容将会对新、旧 CPU 不同! 在 xv6 中, 这种情况唯一一处出现是在 `kernel/proc.c` 中的 `cpuid()` 和 `mycpu()` 函数 (见[第 4 章](ch4.md), 这两个函数定义在 `kernel/proc.c[61:79]`). 具体来说, xv6 在内存中为每个 CPU 核心维护一个 `cpu` 结构体,
> ```c
> // Per-CPU state.
> struct cpu {
>   struct proc *proc;          // The process running on this cpu, or null.
>   struct context context;     // swtch() here to enter scheduler().
>   int noff;                   // Depth of push_off() nesting.
>   int intena;                 // Were interrupts enabled before push_off()?
> };
> ```
> 而我们需要使用 `tp` 作为下标来访问当前 CPU 的 `cpu` 结构体. 这样, 新、旧 CPU 的 `tp` 寄存器的不一致性就会引起它们看到的 `cpu` 结构体不同. 为了保证切换 CPU 后, 新 CPU 看到的 `cpu` 结构体与旧 CPU 的 `cpu` 结构体存储相同的信息, 还应当在切换上下文时把旧 CPU 的 `cpu` 结构体深拷贝到新 CPU 的 `cpu` 结构体. (在[第 12 章](ch12.md)中会看到, 实际上拷贝 `intena` 就足够了.)

## PLIC 硬件

上一小节已详细介绍了 xv6 内核态中断处理的基本流程. 这里我们作一简单的总结: 除去必要的准备工作外, 中断处理入口 `kernelvec()` 调用了 `kerneltrap()`, 而 `kerneltrap()` 又调用了 `devintr()`; `devintr()` 会根据中断产生的原因, 调用相应设备的中断处理器, 来完成中断的最终处理.

这一小节中, 我们来研究 `devintr()` 的具体实现. `devintr()` 函数的定义如下: (`kernel/trap.c[172:220]`)
```c
int devintr()
{
  uint64 scause = r_scause();

  if((scause & 0x8000000000000000L) &&
     (scause & 0xff) == 9){
    // this is a supervisor external interrupt, via PLIC.

    // irq indicates which device interrupted.
    int irq = plic_claim();

    if(irq == UART0_IRQ){
      uartintr();
    } else if(irq == VIRTIO0_IRQ){
      virtio_disk_intr();
    } else if(irq){
      printf("unexpected interrupt irq=%d\n", irq);
    }

    // the PLIC allows each device to raise at most one
    // interrupt at a time; tell the PLIC the device is
    // now allowed to interrupt again.
    if(irq)
      plic_complete(irq);

    return 1;
  } else if(scause == 0x8000000000000001L){
    // software interrupt from a machine-mode timer interrupt,
    // forwarded by timervec in kernelvec.S.

    if(cpuid() == 0){
      clockintr();
    }
    
    // acknowledge the software interrupt by clearing
    // the SSIP bit in sip.
    w_sip(r_sip() & ~2);

    return 2;
  } else {
    return 0;
  }
}
```

在上面的讨论中, 我们已经分析了 `devintr()` 函数的结构. 我们实际上发现, `devintr()` 只会处理两种类型的中断: **supervisor external interrupt** (SEI, 中断码为 9 的外中断, 由外部设备产生) 和 **supervisor software interrupt** (SSI, 中断码为 1 的外中断, 由 M 模式的时钟中断处理程序转发而来). 因此, 我们只要分别讨论这两种中断的处理方式即可.

对于 supervisor external interrupt 的处理, 有一个困难之处: 这类中断可能由形形色色的外部 I/O 设备产生 (如磁盘、键盘、显示器等等), 仅依靠一个中断码 9 完全无法确定中断实际上是由哪个设备产生的. 看起来, 一个更合理的做法似乎是为每一种特定的设备产生的中断分别引入一个单独的中断码 (从而 CPU 可以直接根据中断码判断引起中断的设备), 而非让它们共用同一个中断码. 然而, 这样做虽然让编写操作系统的程序员更轻松了, 却给 CPU 的设计者带来了不便, 因为每当用户想给计算机连接一种新的设备, CPU 的设计者都必须重新发布一版指令集, 来为这台新设备分配中断码. 换言之, 指令集的设计与外部设备的细节高度耦合. 这显然不利于处理器的通用性和兼容性.

因此, 现代计算机系统中通常有一个称为 **中断控制器 (interrupt controller)** 的部件, 该部件的作用是实现中断信号的 **多路复用 (multiplexing)**. 中断控制器一边与 CPU 相连, 一边又连接各种 I/O 设备的端口. 当设备产生一个中断信号时, 该中断信号首先到达中断控制器. 中断控制器根据事先设定好的逻辑, 决定响应或不响应该中断, 以及 (当有多个中断到来时) 响应的优先次序. 一旦中断控制器决定响应某个中断, 它就会给 CPU 发送一个新的中断信号. 无论中断控制器接收到的外部设备中断是什么类型, 它发给 CPU 的新中断信号总是具有相同的中断码. CPU 收到了这个新的中断信号之后, 它发现这个信号是来自于中断控制器的, 于是 CPU 就去读中断控制器暴露给它的控制字; 通过这些控制字, CPU 可以确定具体要处理哪个外部设备的中断. CPU 完成了针对该外部设备的中断处理工作之后, 还会给中断控制器发送一个通知, 使其能够接着响应新的中断 (或队列中优先级更低的中断). 可以看到, 引入中断控制器之后, CPU 不再需要为了一台新增的设备而支持一种新的中断信号 (从而改变指令集). 只需要让中断控制器能够支持该新设备, 并且在操作系统的代码中加入针对该新设备的中断处理逻辑就可以了.

对于 RISC-V 体系结构, 其中断控制器称为 **platform-level interrupt controller (PLIC)**. PLIC 一方面接收各种外部设备产生的中断, 一方面通过给 CPU 发送 supervisor external interrupt 触发 CPU 的中断处理程序. 现在, 作为编写操作系统的程序员, 当我们发现 CPU 收到一个 supervisor external interrupt 时, 要做的事情就是:
* 检查 PLIC 提供的控制字, 确定产生中断的外部设备类型;
* 针对不同设备执行相应的中断处理逻辑;
* 向 PLIC 发送信号, 向它告知中断处理已完成.

当然, 由于 PLIC 自身对于 CPU 来说也是一个外部设备, 在使用 PLIC 之前首先要对它进行一定的初始化. xv6 对 PLIC 的初始化是通过在 `main()` 函数中调用 `plicinit()` 和 `plicinithart()` 来完成的: (`kernel/main.c[25:26]`)
```c
    plicinit();      // set up interrupt controller
    plicinithart();  // ask PLIC for device interrupts
```

> 在阅读这一部分的代码时, 自然要对 PLIC 向程序员提供的编程接口有一定的了解. 对此, RISC-V 关于 PLIC 的官方手册 ([https://github.com/riscv/riscv-plic-spec](https://github.com/riscv/riscv-plic-spec)) 提供了一个相当简明的介绍. 另外, 也可以查阅 RISC-V 特权指令集文档 ([https://riscv.org/wp-content/uploads/2017/05/riscv-privileged-v1.10.pdf](https://riscv.org/wp-content/uploads/2017/05/riscv-privileged-v1.10.pdf)) 的第 7 章. 对于不希望花太多时间阅读源文档的读者, 也可参考以下的简要总结.
>
> 如同其他外部设备一样, PLIC 向程序员提供了一系列 **控制寄存器**. 通过读或写这些控制寄存器, 程序员可以获知或修改 PLIC 硬件的行为. PLIC 提供的控制寄存器分为如下几类:
> * **`priority` 寄存器.** 该寄存器定义了 PLIC 所支持的各种外部中断的优先级. 具体来说, PLIC 为其支持的每一种外部中断都提供一个长为 4 字节的 `priority` 寄存器, 其数值即代表该种中断的优先级. 
>
>   PLIC 最多支持 1023 种外部中断, 用 `[1, 1023]` 范围内的整数唯一地标识每种中断 (标识符 `0` 被 PLIC 保留, 不对应任何外部中断). 因此, `priority` 寄存器实际上有 1024 个, 它们构成共 4096 字节的寄存器堆. 对应于某中断的 `priority` 数值越大, 就表示其优先级越高. 特别地, 当 `priority` 的值为 0 时, 代表禁止响应该种中断.
> * **`pending` 寄存器.** PLIC 为其支持的每种中断提供一个 `pending` 位. 当外部设备向 PLIC 发出一个该种中断的请求时, 会把相应的 `pending` 位设置为 1. 等到 PLIC 收到 CPU 发来的信号, 确认该种中断已被处理完毕后, 会把相应的 `pending` 位清零. 共有 1024 个 `pending` 位, 构成长为 1024 / 8 = 128 字节的寄存器堆.
> * **`enables` 寄存器.** PLIC 为每个 (外部中断, CPU 核心, 特权级别) 的三元组提供一个 `enables` 位. 当某个 `enables` 位为 1 时, 代表允许指定的 CPU 核心在指定的特权级别下响应指定的外部中断. PLIC 把每种 (CPU 核心, 特权级别) 的组合称为一个 **中断上下文**, 且最多支持 15872 种中断上下文. 由于还有 1024 种可能的外部中断 (计及保留的中断标识码 `0`), 故 `enables` 寄存器堆的总长为 1024 * 15872 / 8 = 2031616 字节.
> * **`threshold` 寄存器.** PLIC 还为每种中断上下文提供一个 4 字节的 `threshold` 寄存器. 只有当某种外部中断的 `priority` 值严格大于某种中断上下文的 `threshold` 值时, PLIC 才会允许该中断上下文响应此种中断. 
> * **`claim/complete` 寄存器.** 该寄存器用于处理 PLIC 与 CPU 核心之间的交互逻辑. 对于每种中断上下文, `claim/complete` 是一个 4 字节的寄存器. 其使用方法如下:
>   + 当 CPU 读 `claim/complete` 寄存器时, 如果此时有待处理 (pending) 的外中断, 则该寄存器的值即为这种外中断的标识码; 如果不存在待处理的外中断, 则该寄存器的值为 0.
>   + 当 CPU 处理完某个外中断后, 必须执行一个对 `claim/complete` 寄存器的写操作, 且写入的值须等于该种中断的标识码. 这个写操作相当于对 PLIC 发送了一个确认信号, 表明上一个中断已处理完毕. 只有在这个写操作结束之后, PLIC 才会接着响应其他的外中断.
>
> 上述所有寄存器, 在 PLIC 标准中都被内存映射到了一定的物理地址段. 假如 PLIC 控制寄存器堆的内存映射基址为 `base`, 则上述各寄存器所对应的地址排布如下表所示:
> | 寄存器 | 物理地址范围 |
> |:----:|:------|
> | `priority` | `[base + 0x0, base + 0x1000)` |
> | `pending` | `[base + 0x1000, base + 0x1080)` |
> | `enables` | `[base + 0x2000, base + 0x2080)` 对应中断上下文 `0`, <br>`[base + 0x2080, base + 0x2100)` 对应中断上下文 `1`,<br>... ... |
> | `threshold` <br> `claim/complete` | 这两个寄存器在物理地址空间中交替排布, <br> `[base + 0x200000, base + 0x200004)` 为中断上下文 `0` 的 `threshold`,<br> `[base + 0x200004, base + 0x200008)` 为中断上下文 `0` 的 `claim/complete`,<br> `[base + 0x201000, base + 0x201004)` 为中断上下文 `1` 的 `threshold`,<br> `[base + 0x201004, base + 0x201008)` 为中断上下文 `1` 的 `claim/complete`,<br>... ... |
>
> 在 `kernel/memlayout.h[33:39]` 中通过一系列宏定义给出了 xv6 所要用到的 PLIC 控制寄存器在 `qemu` 下的内存映射地址:
> ```c
> // qemu puts platform-level interrupt controller (PLIC) here.
> #define PLIC 0x0c000000L
> #define PLIC_PRIORITY (PLIC + 0x0)
> #define PLIC_PENDING (PLIC + 0x1000)
> #define PLIC_SENABLE(hart) (PLIC + 0x2080 + (hart)*0x100)
> #define PLIC_SPRIORITY(hart) (PLIC + 0x201000 + (hart)*0x2000)
> #define PLIC_SCLAIM(hart) (PLIC + 0x201004 + (hart)*0x2000)
> ```
> 在我们所用的命令行参数 `-machine virt` 下, `qemu` 将 PLIC 控制寄存器的物理基址 `base` 选为 `0x0c000000`. 接下来几个宏分别代表 `priority`, `pending`, `enables`, `threshold` 和 `claim/complete` 寄存器的基址. 其中, `enables`, `threshold` 和 `claim/complete` 寄存器是每种中断上下文各一个 (或一组) 的, 因此它们的基址还依赖 CPU 的核心号 (`hart`).
>
> 细心的读者可能会注意到, 当核心号 `hart` 等于 0, 1, 2, ... 时, 上面的宏 `PLIC_SENABLE(hart)`, `PLIC_SPRIORITY(hart)` 和 `PLIC_SCLAIM(hart)` 所给出的实际上是相应于中断上下文 1, 3, 5, ... 的 `enables`, `threshold` 和 `claim/complete` 寄存器基址. 事实上, 这是因为中断上下文是 (CPU 核心, 特权级别) 的有序对, 而 RISC-V 中同一个 CPU 核心可以以 M 模式或 S 模式两种特权级别响应中断. 现在 xv6 想要处理的正是 S 模式下的中断, 因此其对应的中断上下文编号就是 1, 3, 5, ....

有了上面的背景知识, 现在我们可以来看看 xv6 具体如何初始化 PLIC: (`kernel/plic.c[11:30]`)

```c
void
plicinit(void)
{
  // set desired IRQ priorities non-zero (otherwise disabled).
  *(uint32*)(PLIC + UART0_IRQ*4) = 1;
  *(uint32*)(PLIC + VIRTIO0_IRQ*4) = 1;
}

void
plicinithart(void)
{
  int hart = cpuid();
  
  // set enable bits for this hart's S-mode
  // for the uart and virtio disk.
  *(uint32*)PLIC_SENABLE(hart) = (1 << UART0_IRQ) | (1 << VIRTIO0_IRQ);

  // set this hart's S-mode priority threshold to 0.
  *(uint32*)PLIC_SPRIORITY(hart) = 0;
}
```
在 xv6 中, 需要在 S 模式下处理的外部中断只有两种来源: (1) UART 设备 (负责控制台输入输出); (2) VIRTIO 设备 (`qemu` 提供的虚拟磁盘设备). 这两种设备所引起的中断在 PLIC 中的标识码已经预设好, 即 `UART0_IRQ = 10` 和 `VIRTIO0_IRQ = 1`. 这样, `plicinit()` 的两行代码就将上述两种设备对应的 `priority` 寄存器设置为 1 (最低的非零优先级), 即允许接收来自它们的中断. 接着, `plicinithart()` 函数为当前 CPU 核心设置 `enables` 和 `threshold` 寄存器, 从而允许当前 CPU 在 S 模式下接收这两种中断.

> `plicinit()` 和 `plicinithart()` 中对于 PLIC 控制寄存器的访问是不是多处理器并发安全的呢? 实际上, 这里的情况和[第 7 章](ch7.md)末尾讨论 `kvminit()` 和 `kvminithart()` 时一样. `plicinit()` (以及 `kvminit()`) 只在 0 号 CPU 上单线程地执行一遍, 故不存在并发访问问题; 而 `plicinithart()` (以及 `kvminithart()`) 写入的是各 CPU 核心私有的寄存器, 同样是安全的.

完成了对 PLIC 硬件的初始化后, 让我们回过头来继续讨论外部设备中断 (supervisor external interrupt) 的处理. 这对应的是函数 `devintr()` 的第一个分支: (`kernel/trap.c[186:203]`)
```c
    // irq indicates which device interrupted.
    int irq = plic_claim();

    if(irq == UART0_IRQ){
      uartintr();
    } else if(irq == VIRTIO0_IRQ){
      virtio_disk_intr();
    } else if(irq){
      printf("unexpected interrupt irq=%d\n", irq);
    }

    // the PLIC allows each device to raise at most one
    // interrupt at a time; tell the PLIC the device is
    // now allowed to interrupt again.
    if(irq)
      plic_complete(irq);

    return 1;
```
在这里, 出现了一对函数 `plic_claim()` 和 `plic_complete()`, 其定义为: (`kernel/plic.c[32:47]`)
```c
// ask the PLIC what interrupt we should serve.
int
plic_claim(void)
{
  int hart = cpuid();
  int irq = *(uint32*)PLIC_SCLAIM(hart);
  return irq;
}

// tell the PLIC we've served this IRQ.
void
plic_complete(int irq)
{
  int hart = cpuid();
  *(uint32*)PLIC_SCLAIM(hart) = irq;
}
```
可以看到, `plic_claim()` 读了 `claim/complete` 寄存器并返回其值. 根据 PLIC 的约定, 该值代表引起中断的设备的标识码. xv6 将 `plic_claim()` 的返回值存储在 `irq` 变量中. 这样, 它就得知了具体是哪种设备引起了 supervisor external interrupt, 从而可以根据不同的设备类型 (UART / VIRTIO / 未知) 调用合适的底层函数与设备进行交互以完成中断处理. 

完成了与设备相关的工作后, xv6 又将 `irq` 传递给 `plic_complete()` 函数. 这个函数将 `irq` 的值写回 `claim/complete`, 因此其含义是向 PLIC 设备传达中断响应已完成的信号. 至此, 对外部中断的处理就结束了.

`devintr()` 的剩余部分是简单的:
```c
  if((scause & 0x8000000000000000L) &&
     (scause & 0xff) == 9){
    // supervisor external interrupt, already discussed above
  } else if(scause == 0x8000000000000001L){
    // software interrupt from a machine-mode timer interrupt,
    // forwarded by timervec in kernelvec.S.

    if(cpuid() == 0){
      clockintr();
    }
    
    // acknowledge the software interrupt by clearing
    // the SSIP bit in sip.
    w_sip(r_sip() & ~2);

    return 2;
  } else {
    return 0;
  }
```
如果 xv6 收到一个 supervisor software interrupt, 它实际上知道这是 M 模式下的时钟中断处理程序所设置的. 当 0 号 CPU 收到此事件时, 它就去调用 `clockintr()` 函数. 这个函数的定义如下: (`kernel/trap.c[163:170]`)
```c
void
clockintr()
{
  acquire(&tickslock);
  ticks++;
  wakeup(&ticks);
  release(&tickslock);
}
```
该函数获取 `tickslock` (这个就是在 `trapinit()` 中初始化的互斥锁) 并把计数器 `ticks` 的数值加 1, 然后唤醒所有因等待计数器增长而睡眠的进程. 之所以要这么做, 是因为 xv6 向用户提供了一个名为 `sleep()` 的系统调用, 它允许用户让进程睡眠一段指定的时间. xv6 在这里将 0 号 CPU 相邻两次时钟中断的时间间隔定义为一个 tick, 而全局变量 `ticks` 就记录自 xv6 启动以来的 tick 数.

> 我们将在[第 13 章](ch13.md)和[第 14 章](ch14.md)中分别详细介绍 xv6 的系统调用及进程的睡眠与唤醒.

接着, xv6 清除 `sip` 寄存器的第 1 位:
```c
    w_sip(r_sip() & ~2);
```
这样, S 模式下就不再有待处理的 supervisor software interrupt. 这句话是对 M 模式下的时钟中断处理函数 `timervec()` 的回应.

最后, 如果 xv6 收到的既不是 supervisor external interrupt, 又不是 supervisor software interrupt, `devintr()` 就返回一个代表未知中断类型的 0 值. 至此, 我们已彻底理解了 xv6 内核模式下的中断处理过程.

## 中断处理中的硬件-软件分工

在本章开头的一小节, 我们曾详细叙述了 RISC-V 硬件的中断响应机制. 硬件能够检测中断的发生, 并在中断发生时提供基本的控制流跳转功能. 然而, 光靠硬件并不足以应对实际计算机系统中复杂多样的中断. 中断处理的核心逻辑离不开 **软件** 的参与. 具体来说, 软件通常需要实现:
* 保存完整的机器状态 (如通用寄存器, 必要的 CSR 和内存中的信息)
* 根据不同的中断码, 或者产生中断的不同设备, 执行相应的处理
* 向产生中断的设备做出回应

不难用本章所讲的具体例子来印证上述一般性的讨论. [下一章](ch11.md)将继续研究 xv6 用户模式下的中断处理.
